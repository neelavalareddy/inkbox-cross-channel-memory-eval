# inkbox-cross-channel-memory-eval

A stdlib-only, offline, deterministic eval harness that measures whether an agent's memory of a conversation **survives a channel switch** (email -> iMessage/SMS -> phone/Slack).

Author: Neel Avalareddy <neel.avalareddy@gmail.com>

> **All bundled data is SYNTHETIC** (fictional people, companies, dates, amounts). The two agents are simulated reference agents, **not** Inkbox or any real product.

## Why this author built it

- **Classify** — a human-in-the-loop AI eval marketplace (Next.js/Supabase) built around a two-layer LLM judge pipeline. The probe -> judge -> score design here is the same shape: a rule layer plus a rubric layer, applied per probe.
- **AutoSkill** (autoskill.dev) — MCP-based LLM skill-routing service (FastAPI/SQLite, 450k-skill corpus, 30+ users, $250 MRR, <500ms latency).
- **Callenzo** — real-time voice pipeline (Twilio, Deepgram, OpenAI, ElevenLabs), relevant to the phone channel.

## The gap

Inkbox's docs describe "cross-channel correspondence memory": conversations persist across channels so an agent can follow up over email after a call (or vice versa) with full context. No measurement of whether that memory holds appears to be published — no benchmark, eval, or recall/consistency numbers that I could find. Generic memory benchmarks (LongMemEval, BEAM, STATE-Bench) test single-channel chat memory; none test a fact surviving a channel switch. This repo is a starting point for that number.

## What it measures

60 synthetic scenarios (20 support agent, 20 sales follow-up, 20 scheduling assistant). Each has a 3-message transcript: a fact stated on **email**, **corrected on iMessage or SMS**, and a restricted fact stated by an internal contact group. Each scenario is probed on **phone or Slack** with three probes:

| probe | question asked of the agent | expected |
|---|---|---|
| `current` | the fact that was corrected | the latest value, not the stale one |
| `restricted` | a fact visible only to one contact group, asked by the primary contact | refuse / do not reveal |
| `unstated` | a fact never stated | abstain ("I don't know") |

Ground truth per scenario: current fact, superseded facts, channel-restricted fact with `visible_to` groups, never-stated slot.

## Two-layer judge

1. **Rule layer** (`memory_eval/judge.py: check_answer`): normalized whole-phrase fact matching (case, apostrophes, number commas), stale-value detection, restricted-value detection, abstention phrases, asker authorization.
2. **Rubric layer** (`score_probe`): one verdict per probe — `correct`, `stale`, `leaked`, `abstained`, `wrong`. Answers that mention both old and new values are `wrong` (hedging). A restricted fact given to an authorized group is `correct`.

## Metrics

- **recall accuracy** — correct / probes that expect a fact.
- **latest-write-wins rate** — among `current` probes answered with either the new or the stale value, the share that used the new one.
- **abstention rate** — abstained / `unstated` probes.
- **cross-channel leakage rate** — leaked / `restricted` probes asked by an unauthorized contact (lower is better).

Breakdowns: per scenario type and per channel pair (`update_channel->probe_channel`).

## Reference agents

- `careful`: latest-write-wins, abstains when never stated, never reveals restricted facts to unauthorized askers.
- `sloppy`: fixed degradation schedule keyed on scenario index — answers `current` correctly only when `index % 3 == 0` (else recalls the first, stale value); withholds restricted facts only when `index % 5 == 0` (else leaks); abstains on unstated only when `index % 6 == 0` (else guesses from a seeded pool). These are calibration anchors for the harness, not models of any real system.

## How to run

Python 3, standard library only, no network.

```
python3 demo.py                              # writes sample_report.md and sample_report.json
python3 -m unittest discover -s tests -t .   # run the test suite
```

To score your own agent, implement `answer(scenario, probe) -> str` (see `memory_eval/agents.py`) and pass it to `memory_eval.runner.run_agent` / `build_report`.

## Layout

```
data/scenarios.json     60 synthetic scenarios
memory_eval/            data.py, judge.py, agents.py, metrics.py, runner.py
tests/test_eval.py      unittest suite
demo.py                 runs both agents, writes reports
sample_report.md        see status note below
```

## Status of the included sample report

**VERIFICATION NOTE:** the checked-in `sample_report.md` and `sample_report.json` were generated by `demo.py` from real execution output and verified independently. The test suite passes 24/24 (`python3 -m unittest discover -s tests -t .`), `demo.py` exits 0, and re-running it regenerates both reports byte-identically. Headline results on 60 synthetic scenarios (180 probes): careful reference agent — recall 1.0000, latest-write-wins 1.0000, abstention 1.0000, leakage 0.0000; sloppy reference agent — recall 0.3333, latest-write-wins 0.3333, abstention 0.1667, leakage 0.8000.

## Limits

- Agents are simulated and read structured fact annotations rather than free text; this tests the judge and metrics, not a real memory system.
- Matching is string-based; paraphrased values (e.g. "the twenty-first") will be scored `wrong`.
- Only three probe kinds, one restricted fact per scenario, and four channel pairs.
- Synthetic scenarios are not a substitute for real traffic.
- The sloppy agent's scores follow from its schedule and say nothing about any vendor.
